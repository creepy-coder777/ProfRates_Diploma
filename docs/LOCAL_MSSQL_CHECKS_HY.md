# Իրական SQL Server-ով ստուգում՝ առանց առկա տվյալները փոխարինելու

Այս միջավայրից ձեր SQL Server-ին հասանելիություն չկա։ Հետևաբար այստեղ իրական MSSQL-ով հաջող փորձարկված գործողությունների ցանկը դատարկ է։ Ստորև հրամաններն աշխատեցնում եք ձեր համակարգչում։ Գաղտնաբառեր, cookie-ներ և token-ներ զրույցում ուղարկել պետք չէ։

## 1. Կառուցվածքի ընթերցում

Նախագծի պանակում `.env`-ում կարգավորեք իրական Server name-ը և DB_NAME-ը, ապա՝

```powershell
.venv\Scripts\python.exe -m tools.check_db
.venv\Scripts\python.exe -m tools.export_schema
.venv\Scripts\python.exe -m tools.verify_schema
```

Ուղարկելու համար նախատեսված արդյունքները՝ `exports/schema_metadata.json` և `exports/schema_verification.json`։ Սրանք տվյալների տողեր չեն արտահանում։ Module-ների սահմանումներում ներկառուցված գաղտնի արժեքների բացակայությունը նախ ստուգեք տեղային միջավայրում։ `.env`-ը մի ուղարկեք։

Ստուգիչը համեմատում է SQL Server-ի իրական metadata-ն `docs/schema_contract.json`-ի հետ՝

- Օբյեկտի տեսակը՝ աղյուսակ կամ view, դաշտի անունը և SQL տեսակը։
- Աղյուսակների տեքստային դաշտերի երկարությունը՝ բայթերով. օրինակ `nvarchar(150)`-ը `max_length=300` է։
- Աղյուսակների NULL թույլատրելիությունը և IDENTITY հատկությունը։
- Primary key, Foreign key և Unique key սյունակներն ու հերթականությունը։ FK-ն պետք է լինի միացված և վստահելի, index-ը՝ միացված։ Ստուգվում է նաև անհրաժեշտ filtered unique index-ը։
- Առանց default-ի անսպասելի նոր պարտադիր դաշտերը։
- Օգտագործվող view-երի հայտնի տեսակներն ու սահմանումների տեքստի համեմատությունը։

View-ի հաշվարկային որոշ դաշտերի NULL/երկարության metadata-ն արտահանված SQL-ից վստահորեն չի հաստատվում և բացահայտ նշված է `view_metadata_not_asserted` բաժնում։ CHECK/default կանոնների և trigger-ների ամբողջական վարքը չի հաստատվում միայն այս ստուգումով։ Տեքստի համընկնումը նույնպես runtime թեստ չէ։

Արդյունքի կոդեր՝ 0՝ կառուցվածքային ստուգումն անցել է առանց view/trigger վերանայման ազդանշանի, 1՝ անհամապատասխանություն կամ թերի metadata, 2՝ կառուցվածքը համընկնում է, բայց view-ի սահմանում կամ ակտիվ trigger պետք է ուսումնասիրել։ Ոչ մի կոդ ինքնուրույն չի հաստատում backup-ի հետ համապատասխանությունը կամ runtime վարքը։

Եթե app հաշիվը չունի VIEW DEFINITION, արտահանումը պետք է կատարի բազայի սեփականատերը կամ համապատասխան իրավունք ունեցող պատասխանատուն։ Գործիքները ինքնուրույն իրավունք չեն շնորհում։

Այլընտրանք՝ SSMS → բազայի վրա աջ կոճակ → Tasks → Generate Scripts → ամբողջ բազայի օբյեկտները → Advanced → `Types of data to script = Schema only`։ Միացրեք Trigger/Index/Primary Key/Foreign Key/Unique Key/Check/Default արտահանումը, ներառեք view-երը, function-ները և procedure-ները։ Պահպանեք Unicode-ով՝ `ProfRates_live_schema.sql` անունով։ Այն պետք է արտահանել, ոչ execute անել։

## 2. Արդյոք script.sql-ը վերջնական backup-ի՞ց է

Այս փաթեթը չի պնդում, որ դա հաստատված է։ Երկու ֆայլերի SHA-256-ները պահպանված են `docs/schema_contract.json`-ի `source` բաժնում։ Նույն hash-ը հաստատում է միայն ֆայլի նույնությունը, ոչ SQL-ի և backup-ի schema-ների հավասարությունը։

Backup-ի անունը և ընթացիկ բազայի անունը նույնպես բավարար ապացույց չեն։ `docs/BACKUP_PROVENANCE_READONLY.sql`-ը տալիս է միայն ընթերցման հարցումներ՝ ընթացիկ բազայի և restore history-ի մասին։ Backup-ի HeaderOnly հրամանը վերադարձնում է backup-ի վերնամասի տեղեկությունը, բազա չի վերականգնում։ Հրամանի ֆայլային ուղին պետք է հասանելի լինի SQL Server ծառայությանը, ոչ միայն ձեր համակարգչի SSMS-ին։

SSMS-ում նույն բազան ընտրած՝ բացեք այդ ֆայլը։ Կարող եք ստանալ DatabaseName, backup-ի ժամանակները, BackupSetGUID/LSN-ները և համեմատել restore history-ի հետ։ HeaderOnly-ի համար կարող է պահանջվել ավելի բարձր իրավունք։ Այդ տեղեկությունները ցույց են տալիս ծագման կապը, բայց չեն բացառում restore-ից հետո կառուցվածքային փոփոխությունները։

Եթե անհրաժեշտ է վերջնական backup-ի schema-ի խիստ համեմատություն, պետք է ստանալ արդեն այդ backup-ից վերականգնված բազայի կառուցվածքային արտահանում կամ առանձին համաձայնությամբ այն վերականգնել մեկուսացված նոր բազայի անունով։ Այս փաթեթը restore, DROP, CREATE DATABASE կամ ընթացիկ բազայի փոփոխություն չի կատարում։

## 3. MSSQL-ի ծառայությունների փորձարկում՝ ROLLBACK-ով

Սա տեղային CLI ստուգում է՝ ձեր DB connection-ի իրավունքներով։ Այն HTTP login կամ ադմին API-ի շրջանցում չէ։ Այն չի ապացուցում առաջին ուսանողի նույնականացման ճիշտ աշխատանքը կամ commit-ից հետո Frontend-ի պահպանումը։

Սկզբում միայն ընթերցում՝

```powershell
.venv\Scripts\python.exe -m tools.smoke_mssql
```

Եթե կառուցվածքը համապատասխանում է, ձեր իրական `Admins.AdminID`-ով աշխատեցրեք՝

```powershell
.venv\Scripts\python.exe -m tools.smoke_mssql --write-rollback --admin-id 1
```

`1`-ը փոխարինեք գոյություն ունեցող ադմինի իրական ID-ով։ Այստեղ գաղտնաբառ չի փոխանցվում. գործիքը բազային միանում է ձեր տեղային `.env`-ի միջոցով։ Նոր ադմին հաշիվ չի ստեղծվում։

Գործիքը մեկ transaction-ում ստեղծում է `S2TEST_...` նշումով նոր դասախոսներ, ուսումնական օբյեկտներ, ժամանակավոր ուսանող, կապ, հարց և գնահատում/պատասխանների fixture։ Ժամանակավոր ուսանողն ունի մուտքի համար չօգտագործվող գաղտնաբառի արժեք և չի պահպանվում transaction-ից դուրս։ Սա գրանցման կամ գնահատումների նոր backend իրականացում չէ, միայն թեստային տվյալ է։ Օգտագործվում է արդեն գոյություն ունեցող AcademicSemesters գրառում. դրա բացակայությամբ գործիքը դադարում է։

Ստուգվում են ավելացումը, փոփոխումը, որոնումը, ամբիոնի ֆիլտրը, ուսումնական կապերը, հարցի նոր տարբերակը՝ հին պատասխանի պահպանմամբ, հաստատում/մերժում և live summary/public view-երի արդյունքները։ Փոփոխվում կամ ապաակտիվացվում են միայն այս գործիքի ստեղծած օբյեկտները։ Ամբողջ ակտիվ հարցաշարի ընդհանուր հերթականությունը չի վերագրվում։ Վերջում բոլոր փոփոխությունները, ներառյալ audit գրառումները, ROLLBACK են արվում, իսկ նոր connection-ով ստուգվում է fixture-ների բացակայությունը։

Կարևոր սահմաններ՝ IDENTITY համարակալման մեջ կարող են բացեր մնալ նաև ROLLBACK-ից հետո. գործիքը չի reseed անում համարները։ SERIALIZABLE transaction-ը կարող է ժամանակավորապես արգելափակել այլ գործողություններ, ուստի այն գործարկեք տեղային հանգիստ միջավայրում։ Արտաքին side effect ունեցող trigger-ի կամ audit provider-ի գործողությունը SQL rollback-ը պարտադիր չի վերացնում։ Արտաքին AUDIT_PROVIDER-ի դեպքում գործիքը հրաժարվում է գրել։ Ակտիվ trigger կամ view-ի տարբեր սահմանում հայտնաբերելիս նախ ուսումնասիրեք դրանք. միայն դրանից հետո կարելի է օգտագործել `--reviewed-behavior` տարբերակը։ Անհայտ վարքի դեպքում պարզապես ուղարկեք սահմանումները և մի շարունակեք գրառումների փուլը։

Արդյունքը՝ `exports/mssql_smoke_report.json`։ Հաջող կարգավիճակը `passed_rollback_only` է։ Այն հստակ պարունակում է `authentication: NOT_TESTED` և `committed_api_persistence: NOT_TESTED`։

## 4. Իրական նույնականացումից հետո՝ API և էջերի պահպանում

Նախ կատարեք `docs/AUTH_CONNECTION_HY.md`-ի քայլերը։ Այնուհետև՝

```powershell
.venv\Scripts\python.exe -m tools.check_auth --mode token
```

Cookie session-ի դեպքում օգտագործեք `--mode cookie`։ Իրական token-ը կամ Cookie header-ը հարցվում է տեղային թաքնված մուտքով և չի պահպանվում հաշվետվությունում։ Եթե դա հարմար չէ, նույն հարցումները ստուգեք արդեն մուտք գործած բրաուզերի Network բաժնում։ Սպասվող պատասխաններ՝ առանց login-ի 401, կեղծ role/token-ով 401, իրական ադմինով `/api/admin/integration-status`՝ 200, իրական ուսանողով ադմին գործողություն՝ 403։

Գործնական UI ստուգման համար օգտագործեք նոր `S2UI_...` անուններով գրառումներ և պահեք դրանց ID-ները։

| Գործողություն | Ինչ ստուգել |
| --- | --- |
| Նոր դասախոս ավելացնել | API 201, էջը թարմացնելուց հետո նույն ID-ն և անունը մնում են |
| Խմբագրել | API 200, նորից բացելուց հետո փոխված տվյալներն են |
| Որոնել | Անուն/ազգանուն, ամբիոնի ֆիլտր և էջավորում |

Այս UI քայլերն արդեն commit են անում ձեր նոր test գրառումները։ Մաքրելու համար ապաակտիվացրեք միայն ձեր ստեղծած օբյեկտները, հեռացրեք միայն ձեր ստեղծած ուսումնական կապերը և մերժեք test մեկնաբանությունները։ Պատմություն ունեցող հարցերն ու գնահատումները SQL-ով կուրորեն մի ջնջեք։ Անհրաժեշտության դեպքում այս վերջնական UI փորձարկումները կատարեք առանձին համաձայնեցված test բազայում։

Մինչ առաջին/երրորդ բաժինների միացումը վերջին աղյուսակի բոլոր քայլերը կատարված չեն համարվում։ Միայն testclient-ի կամ CLI-ի հաջողությունը չի փոխարինում իրական login → API → MSSQL → էջի թարմացում շղթային։
